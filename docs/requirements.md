**子路徑為什麼是最大的不確定性**:版型裡至少 16 處寫成 `{{ "/tags/" | relURL }}` 這種
「開頭帶斜線再過 `relURL`」的形式(`404.html`、`search.html`、`header.html`、`footer.html`、

## Define —— 這次要解決的問題

### 問題陳述

站主已經有一套用得順手的部落格版型,但它的原始碼鎖在私有 repo、建置跑在自家的機器上,
公開的那一端只有 HTML 成品 —— 讀者看不到原稿,也看不出這個站是怎麼做出來的,
而且整條產線要靠家裡的設備活著。
站主想要同一套架構的另一個版本:**原稿、版型、建置、託管全部在一個公開 repo 裡**,
寫完 Markdown 推上去就發布,repo 本身就是拿得出手的作品。
這個專案同時用來測三支新寫的開發流程 skill,所以過程留下的痕跡也是成果的一部分。

**要做**

- 從正本搬版型、樣式、腳本、設定、文章範本與 Hugo 版本釘點 —— **用白名單搬,不是整包複製**

## Develop —— 考慮過的做法

產生器、版型、部署平台都已經由「照原架構、改回 GitHub 建置」決定了,
所以這裡攤開來比的是**怎麼把它搬過來**,以及搬的過程中幾個會影響結果的小決定。

### 主要決定:怎麼搬

| 做法 | 怎麼運作 | 優點 | 代價與風險 |
|---|---|---|---|
| **A. 整包搬,再刪改** | 第一筆就把白名單裡的版型、樣式、腳本、設定(約 2,300 行)一次放進來,接上 workflow 先讓站上線;之後再用幾筆 commit 清舊產線殘留、修子路徑 | 最快看到完整的站;原架構的行為原封不動,不容易漏功能 | 第一筆 commit 就把 2,300 行送進收不回的公開歷史,要在那之前把每一行看完,等於把風險最高的檢查壓在最前面一次做完;子路徑問題要等整包進來才會現形,而且會一次壞一片;commit 歷史是「倒一包、再修」,當作品看沒有說服力;整合次數少,三支 skill 練不到幾次 |
| **B. 先走通一條線,再一片一片加回來** | 第一片只放最小的骨架(設定 + 基本版面 + 首頁 + 文章頁 + workflow),部署到 `/BDGG_blog/`,先把「GitHub 建置部署」和「子路徑」這兩個最不確定的點驗掉;之後每個功能一片:分區與列表、標籤、RSS、搜尋、留言、程式碼複製、進度條、分享、系列文、封面、404、關於頁。每一片進來前看過、能單獨建置、能單獨上線 | 最不確定的事最先驗,錯了回頭的成本最低;每個檔案是在輪到它的那一片被看過才進公開歷史;`main` 每一筆都能發布;commit 歷史讀起來就是這個站怎麼長出來的;三支 skill 各會被用到十幾次,測得出好不好用 | 筆數多(估 12 – 15 片),整體比 A 慢;版型之間互相引用(`baseof` 引 `head` / `header` / `footer`,列表引 `entry`),切片時要處理好相依,否則某一片會建不起來;中間幾天線上的站是不完整的 |
| **C. 連同歷史一起搬** | 用 `git filter-repo` 從 GitLab 正本濾出白名單路徑,保留原本 58 筆 commit 的歷史,推到 GitHub 後再往上改 | 保留真實的開發歷史,當作品集最有份量 | 歷史裡每一筆的每個版本都會公開:舊文章內容、內網相關的註解、當時的設定值全在裡面,要逐筆審過才能推,工作量遠大於 A、B,漏看一處就收不回;而且會把「不帶舊內容」這個決定打破 |

**建議 B。** 理由有三個,依重要性排:

1. 這個專案最硬的限制是「公開歷史收不回」,而來源是私有 repo。B 是唯一讓每個檔案在進來前被單獨看過的做法
2. 子路徑是目前最大的未知,B 在第一片就會碰到它;A 要到整包進來才知道
3. 站主的目的之一是測三支 skill。B 的每一片都是一次完整的「同步 → 做一小步 → 建置 → 整合」,也是一次 commit 訊息的練習

C 不建議:它直接撞上限制條件,而且和已確認的範圍矛盾。

另外想過但沒列進來比的一條路:把版型抽成獨立的 Hugo module,讓 GitLab 正本和這個 repo 共用同一份。
它能解決「兩邊版型日後各改各的」這個問題,但需要動 GitLab 正本,超出這次的範圍。先記在這裡。

## Deliver —— 小範圍測試與結果

> 每一項功能測了什麼、量到什麼,細節在 [`features.md`](features.md) 的「已定下的做法」;過程中回頭改了哪些結論,在下面的「回頭修正」。

### 怎麼測的

八項功能用的是同一套做法,第一項定下來之後沒有換過:

- **最不確定的先用丟棄用的小站試**。功能 1 只放兩個互相連結的頁面,先把「GitHub 建置部署」與「子路徑」驗掉,才開始搬版型。
- **假內容只放在暫存區**。把 repo 複製一份、疊上刻意刁鑽的假文章(很長的網址與標題、寬表格、中文與含符號的標籤、
  草稿、日期在未來的文章、多到要分頁的篇數),在那裡建置與量測。假文章從頭到尾沒有進過這個 repo。
- **用瀏覽器量,不用讀的**。無頭 Chrome 開每一種頁面,在 360px 淺色、360px 深色、1280px 三種畫面下記錄:
  有沒有橫向捲動、有沒有 400 以上的回應、console 有沒有錯誤;複製鈕、排序、搜尋都是實際操作後把結果讀回來比對。
- **檢查器先確認會叫**。成品檢查的每一種要擋的情況都有一個假成品(54 個測試,`make check` 每次先跑它們);
  量測的方法也一樣 —— 先把防橫向捲動的樣式關掉,確認量得到問題,才相信它量到的「沒有問題」。
- **線上再對一次**。功能 2 起,每次 push 之後把線上的每個檔案抓回來,和本機同一筆 commit 的成品逐位元比對。

### 淘汰的做法與原因

  ⑤ 規格沒列 `make new`,但 Hugo 不在 PATH 上,少了它文章範本用不到,所以加了。
  另外,第一篇文章的內容站主只給了題目,由 agent 當場實測後起草,發布前給站主看過大綱並取得同意。
  細節在 `features.md` 的「文章頁(功能 3)」。

- **Deliver(功能 4)→ Define(2026-10-05)**:規格與實際情況有四處對不上,都是查核與實測時才看到的。
  ① **`robots.txt` 在子路徑底下沒有作用** —— 爬蟲只讀網域根的那一份(RFC 9309),而網域根不歸這個 repo 管。
  「搜尋引擎拿到正確的網址」因此不能靠 robots.txt 指出 sitemap,要由站主到站長工具提交;
  這一項原本寫「不需要站主」,實際上有一件只有站主能做的事(還沒做,不影響其餘驗收)。檔案仍照規格產出。
  ② 基礎架構盤點寫 RSS「不用動」。原版型原樣搬過來,W3C Feed Validator 是無效(3 個錯誤),
  而且只收三個分區 —— 這個站的第一篇不在裡面,feed 會是空的。
  ③ 驗收寫「sitemap 與 robots 不得含 `http://`」。sitemap 的命名空間名稱本身就是 `http://` 開頭,
  照字面檢查每次都會失敗;改成檢查裡面每一個網址的值。
  ④ 規格沒提到的一個坑:不明寫輸出格式的話,功能 5 一打開分區頁,每個分區都會多出一份內容相同的全站 feed。
  這次先在設定裡擋掉。
  另外原版型的頁首有兩個在原站沒被發現的問題(首頁的說明取到內文、說明文字跳脫兩次),一併改了。
  細節在 `features.md` 的「被找到與被訂閱(功能 4)」。

- **Deliver(功能 5)→ Define(2026-10-05)**:列表照規格搬,有五件事是查核與實測時才知道的。
  ① 規格把「空的分區要不要掛選單」留給這一項決定。原架構是不掛,做法是手動註解設定;
  那樣的話站主在一個新的分區發第一篇文時,還得記得回去改設定,和「push 就上線、零手動步驟」對不上。
  改成六個分區都寫在設定裡、沒有文章的自動不顯示。
  ② 原版型首頁的分區卡片是從選單的網址切出分區名稱,**在子路徑下一張都對不上** ——
  又一處原站建在網域根目錄所以從來沒有機會出現的問題,而且它不會讓建置失敗、連結檢查也看不出來(卡片只是不見)。
  ③ 分頁第 2 頁以後的 canonical 指向第 1 頁。功能 4 做 canonical 時還沒有任何會分頁的頁面,所以沒有遇到;
  成品檢查因此多了「canonical 要等於這一頁自己的位置」一項。
  ④ 規格的目標寫「文章多了可以分頁與排序」。原版型的設計是兩者**不會同時出現**:分區一分頁,排序按鈕就拿掉
  (前端排序只能排當頁)。照搬了這個設計;文章多了之後要排序,走不分頁的「最新」頁。
  ⑤ 原版型的首頁不收「速查」分區。沒有照搬,首頁、「最新」頁與 RSS 現在收的是同一批文章。
  另外有兩件留給站主的事:分區的一句話簡介與介紹文字沒有寫(那是站主的文案,舊的不帶);
  首頁仍然留著「這個站還在搭建中。」這一句。
  細節在 `features.md` 的「分區與首頁列表(功能 5)」。

- **Deliver(功能 6)→ Define(2026-10-05)**:標籤照規格做,有四件事是查核與實測時才知道的。
  ① 規格把 `term-name.html` 列在範圍內(原架構用它還原標籤的大小寫)。實測 Hugo 有一個現成的設定
  (`capitalizeListTitles = false`),關掉之後標籤頁的標題就是作者寫的樣子,所以那支 partial 沒有搬。
  ② 同一個標籤有兩種寫法時(`MCP` 與 `mcp`),Hugo 把它們併成一頁,但顯示哪一種**每次建置不一定相同** ——
  和驗收第 5 項(本機與 CI 的成品一致)直接衝突,而且規格沒有料到。原架構是「以最新的那一篇為準」;
  這裡改成建置失敗並指出是哪兩篇。這會讓「push 就上線」多一種失敗的原因,是替站主做的決定,可以改回去。
  ③ 原版型用標籤名稱自己組網址,`C#` 這種標籤的連結是壞的 —— 又一處在原站沒有機會出現的問題(原站沒有這種標籤)。
  ④ 驗收寫「中文標籤的網址在子路徑下打得開」。線上唯一的一篇文章沒有中文標籤,所以這一條是在本機的同一個子路徑下驗的,
  線上要等第一篇帶中文標籤的文章。
  另外基礎架構盤點寫標籤「不用動」;實際上除了連結的寫法,還有分頁的 canonical 與手機版面各一處要改。
  細節在 `features.md` 的「標籤(功能 6)」。

- **Deliver(功能 7)→ Define / Discover(2026-10-05)**:關於頁本身照規格做,有四件事和原先寫的不一樣。
  ① **「真名」**:已確認的事實第 4 項寫關於頁放真名。站主貼需求時那一欄填的是 BDGG,所以頁面只以筆名自稱。
  ② **「做過什麼」只做到一半**:站主要的是「簡單說明工作經歷與工作技能」,但沒有給事實,agent 也沒有來源可以查
  (公開的 GitHub 個人頁是空的)。技能由 agent 起草、站主看過同意;工作經歷站主選擇先不放。
  目標裡的「做過什麼」目前只有「這個站」一段。
  ③ **功能 1 定下的一道防線其實沒有在作用**:「選單指到不存在的頁面時成品檢查會擋」。
  實測 `--minify` 之後空的 `href` 連等號都不剩,檢查器把它跳過了,而對照組測試餵的是沒有 minify 過的寫法。
  這是在查「關於頁還是草稿時先掛選單會怎樣」的時候看到的,先單獨修掉再做關於頁。
  功能 1 的回頭修正 ③ 記過同一類的事(`--minify` 拿掉引號讓 `grep` 失效),當時只處理了引號。
  ④ 規格列的「作者欄旁的匿名規則註解改寫」沒有東西可改 —— 那段註解功能 2 就沒有搬進來;新寫了一行說明筆名。
  另外,原版型為關於頁準備的技能標籤樣式沒有用(要在 Markdown 裡寫 HTML),已刪。
  細節在 `features.md` 的「關於頁(功能 7)」。

- **Deliver(功能 8)→ Define / Develop(2026-10-05)**:搜尋照規格做,有四件事是查核與對照之後才定的。
  ① **沒有照規格用 `data-baseurl`**。規格擔心的是那個屬性在子路徑下寫錯;實測照「已定下的做法」寫是對的,
  但對照出另一個問題:索引檔哪天沒被產生(設定少了一個字),`make check` 照樣通過,要到讀者按下搜尋才壞。
  改成由版型把索引檔的位置算好交給腳本,同樣的情況建置會直接失敗,成品檢查也只要把它當成另一種站內連結。
  ② 基礎架構盤點寫搜尋「不用動;中文搜尋要實測」。實測中文子字串比對本身沒有問題,
  但原版型索引的是 Markdown 原稿 —— 一句話中間只要有粗體或連結,照頁面上的字搜就找不到。改成索引頁面上看到的字。
  ③ 原版型的 404 搜尋有四個在原站沒被發現的問題(結果上的分區顯示成目錄名、重新整理會蓋掉讀者打的字、
  網址有落單的 `%` 時腳本出錯、超過 30 篇時數字和列表對不上),都是拿原版的腳本在測試站跑過才看到的。
  ④ 驗收寫「成品檢查涵蓋 `index.json`(不得出現 `192.168.`)」。那一項功能 1 就有了;真正缺的是索引裡的**網址**與**草稿** ——
  搜尋結果是瀏覽器裡的腳本畫出來的,原本的檢查(看 HTML 的連結與草稿標記)完全看不到,所以補了這兩項。
  另外有一件替站主做的決定:**關於頁搜不到**(索引只收文章)。細節在 `features.md` 的「站內搜尋(功能 8)」。
