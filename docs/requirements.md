## Develop —— 考慮過的做法

產生器、版型、部署平台都已經由「照原架構、改回 GitHub 建置」決定了,
所以這裡攤開來比的是**怎麼把它搬過來**,以及搬的過程中幾個會影響結果的小決定。

### 主要決定:怎麼搬

| 做法 | 怎麼運作 | 優點 | 代價與風險 |
|---|---|---|---|
| **A. 整包搬,再刪改** | 第一筆就把白名單裡的版型、樣式、腳本、設定(約 2,300 行)一次放進來,接上 workflow 先讓站上線;之後再用幾筆 commit 清舊產線殘留、修子路徑 | 最快看到完整的站;原架構的行為原封不動,不容易漏功能 | 第一筆 commit 就把 2,300 行送進收不回的公開歷史,要在那之前把每一行看完,等於把風險最高的檢查壓在最前面一次做完;子路徑問題要等整包進來才會現形,而且會一次壞一片;commit 歷史是「倒一包、再修」,當作品看沒有說服力;整合次數少,三支 skill 練不到幾次 |
| **B. 先走通一條線,再一片一片加回來** | 第一片只放最小的骨架(設定 + 基本版面 + 首頁 + 文章頁 + workflow),部署到 `/BDGG_blog/`,先把「GitHub 建置部署」和「子路徑」這兩個最不確定的點驗掉;之後每個功能一片:分區與列表、標籤、RSS、搜尋、留言、程式碼複製、進度條、分享、系列文、封面、404、關於頁。每一片進來前看過、能單獨建置、能單獨上線 | 最不確定的事最先驗,錯了回頭的成本最低;每個檔案是在輪到它的那一片被看過才進公開歷史;`main` 每一筆都能發布;commit 歷史讀起來就是這個站怎麼長出來的;三支 skill 各會被用到十幾次,測得出好不好用 | 筆數多(估 12 – 15 片),整體比 A 慢;版型之間互相引用(`baseof` 引 `head` / `header` / `footer`,列表引 `entry`),切片時要處理好相依,否則某一片會建不起來;中間幾天線上的站是不完整的 |
| **C. 連同歷史一起搬** | 用 `git filter-repo` 從 GitLab 正本濾出白名單路徑,保留原本 58 筆 commit 的歷史,推到 GitHub 後再往上改 | 保留真實的開發歷史,當作品集最有份量 | 歷史裡每一筆的每個版本都會公開:舊文章內容、內網相關的註解、當時的設定值全在裡面,要逐筆審過才能推,工作量遠大於 A、B,漏看一處就收不回;而且會把「不帶舊內容」這個決定打破 |

**建議 B。** 理由有三個,依重要性排:

1. 這個專案最硬的限制是「公開歷史收不回」,而來源是私有 repo。B 是唯一讓每個檔案在進來前被單獨看過的做法
2. 子路徑是目前最大的未知,B 在第一片就會碰到它;A 要到整包進來才知道
3. 站主的目的之一是測三支 skill。B 的每一片都是一次完整的「同步 → 做一小步 → 建置 → 整合」,也是一次 commit 訊息的練習

C 不建議:它直接撞上限制條件,而且和已確認的範圍矛盾。

另外想過但沒列進來比的一條路:把版型抽成獨立的 Hugo module,讓 GitLab 正本和這個 repo 共用同一份。
它能解決「兩邊版型日後各改各的」這個問題,但需要動 GitLab 正本,超出這次的範圍。先記在這裡。

### 選定的做法、8 項功能需求與順序

**站主選定 B(2026-10-05),並把功能收成 8 項(同日定案)。**
次要決定站主沒有另外表示意見,暫時照上表的建議。

**為什麼是這 8 項。** 站主問「哪些功能最能讓人想用下去」,判斷依據是:
部落格用不用得下去,主要看作者會不會繼續寫,讀者功能排在後面。
正本的數字是佐證 —— 已發布 1 篇、草稿 30 篇,版型功能很齊全,卡住的是發布這一步。
所以「發一篇文章有多省事」排第一,「文章頁好不好讀」排第二,其餘依讀者怎麼來、怎麼留下來排。

| 重要性 | 功能需求 | 為什麼重要 |
|---|---|---|
| 1 | push 就上線 | 寫完到上線中間沒有關卡,本機預覽和線上一樣;作者才會繼續寫 |
| 2 | 文章頁的閱讀體驗 | 技術部落格的讀者多半從搜尋引擎直接落在單篇文章上,這一頁就是整個站 |
| 3 | 基本版面 | 導覽、深色模式、手機版面、載入快 |
| 4 | 被找到與被訂閱 | 流量主要來自搜尋;會回來的讀者靠 RSS |
| 5 | 分區與首頁列表 | 四類內容混在一起,讀者要能只看一類 |
| 6 | 標籤 | 跨分區找同主題的文章 |
| 7 | 關於頁 | 當作品集,這頁是門面 |
| 8 | 站內搜尋 | 文章少於幾十篇時用處不大,是 8 項裡最弱的;文章多了之後才顯出價值 |

**放掉的,以及理由**:留言(多數技術部落格留言很少,還要多維護一個外部服務)、
分享按鈕與閱讀進度條(很少有人用)、系列文導覽與相關文章(要等文章多到有系列才有用)、
封面與穿插照片(純裝飾,而且這次不帶照片)。之後要加,每一項都可以是獨立的一片。

**實作順序**照重要性排,只有一處因為相依而對調:基本版面(重要性 3)要先於文章頁(重要性 2),
因為文章頁需要版面骨架與樣式才能讀。排序的原則:

1. **最不確定的先做** —— GitHub 建置部署與子路徑放在最前面,錯了回頭最便宜
2. **每一片做完都能單獨上線**,`main` 上不留做到一半的東西
3. **第 3 片做完,這個站就已經能發文、能讀**;之後每一片都是在可用的站上加東西

版型之間的引用關係會影響怎麼搬:

- `baseof` 引用 `head`、`header`、`footer`,以及複製、進度條、分享三支腳本
- `head` 引用封面解析來產生社群分享圖
- `single` 引用留言、封面、穿插照片、系列文、分享、文章摘要卡
- `list`、`index`、`latest` 都引用文章摘要卡(`entry`),`entry` 又引用封面
- `404` 與搜尋頁共用 `search.js`

其中留言、封面、穿插照片、系列文、分享、進度條都不在範圍內,所以對應的引用是**直接拿掉,不會再加回來**;
社群分享圖改成固定用預設那一張。在範圍內但還沒輪到的引用(摘要卡、搜尋),版型先以精簡的形式進來,輪到時再補上。
樣式檔 `main.css`(657 行)在第 2 片整份看過後進來,同時刪掉不在範圍內的功能所用的樣式。

| 片 | 功能需求 | 做完之後能做到什麼 | 主要內容 | 怎麼驗 | 需要站主 |
|---|---|---|---|---|---|
| 開工前 | — | repo 有說明與授權,可以開始收 commit | 這份紀錄、`.gitignore`、授權檔(MIT + CC BY 4.0)、最簡 README | 未登入能在 GitHub 上讀到 | 同意第一次 push 到公開 repo |
