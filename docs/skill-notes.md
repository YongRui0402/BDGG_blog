# 三支 skill 的試用心得

> 每做完一項功能記一筆:哪裡有幫助、哪裡卡住或多餘。收尾時彙整。
> 記錄的人是實際照 skill 做事的 agent,寫的是做的當下遇到的事,不是事後的評價。

## 功能 1:push 就上線(2026-10-05)

### double-diamond-principle

**有幫助**

- 「需求已經很明確 → Discover 縮成查核」這一列很好用。這次的規格很完整,
  照它做的是核對規格和現況有沒有矛盾,而不是重問一輪需求。
- Deliver 的「先小規模試、驗最不確定的那一點」直接帶來這次最有價值的結果。
  在暫存區用一個丟棄用的小站實測,十分鐘內推翻或補上了四件事:選單的 `url` 其實會補子路徑、
  `languageCode` 已棄用、Hugo 不清舊頁面、`--minify` 會讓舊的草稿檢查失效。這些都不在規格裡。
- 「每個階段結束問一句:剛學到的有沒有動搖前面的結論」促成了回頭改 `requirements.md` 的假設清單。

**卡住或多餘**

- 規格已經由前一次對話寫成 `requirements.md` 與 `features.md`,這時「留下紀錄」的完整版範本和既有文件高度重疊。
  skill 沒有說「已經有 brief 的時候,紀錄要寫在哪、寫多少」。這次的做法是只把新學到的事寫回既有文件,不另開一份。
- Develop 要求「多個真正不同的做法」。這一項的大方向早已定案,能攤開的只剩小決定
  (檢查腳本用什麼寫、失敗測試怎麼做),硬湊三個方案會很假。
  不過其中一個小決定確實挖出規格裡的矛盾(見 trunk-based-development),所以這一步不算白做。

### git-conventional-commit

**有幫助**

- 「測試跟著它驗證的那筆變更走」「拆開後每一筆都要能獨立建置」兩條直接決定了切法:
  Makefile、站台、檢查腳本與它的測試放在同一筆 `feat`,因為少了任何一塊 `make check` 都跑不起來。
- revert 的寫法(`revert` type + `Refs:` 列出被還原的 SHA)有現成範例,不用想。
- 隨附的 `check_commit_msg.py` 在提交前跑一次很省事,每一筆都一次過。

**卡住或多餘**

- type 表對兩種情況沒有答案:① 鋪路 commit 同時有文件、授權檔與 `.gitignore`(選了 `chore`);
  ② 一筆「故意弄壞、馬上還原」的測試用 commit(選了 `test`,但它其實不是在補測試)。
- 全新的 repo 沒有既有歷史可以參考,「description 用使用者與你溝通的語言」這一句是唯一的依據,夠用。

### trunk-based-development

**有幫助**

- 「提交前在本機跑和 CI 同一道建置」是這一項的骨幹,直接變成 `make check` 與 workflow 的設計。
- 「整合完成 = 落地後 trunk 的 CI 是綠的」讓每次 push 之後都去看 Actions 的結果,而不是推完就算。
- 「自己弄壞了就立刻 revert」在失敗測試那一段照著做:紅燈從 push 到還原約一分半鐘。

**卡住或多餘**

- **skill 的第一條承諾(不弄壞建置)和這一項的驗收條件(故意推一筆建不起來的變更到 `main`)正面衝突**,
  skill 裡沒有「刻意的紅燈」這種情況的指引。這次是把兩個做法(暫時 branch 手動觸發/照原文推到 `main`)
  攤給站主選,站主選了後者。建議 skill 補一段:要驗證「壞掉的建置不會發布」時該怎麼做。
- 開工前的指令在空的 remote 上跑不了:`git symbolic-ref refs/remotes/origin/HEAD` 與 `git pull --rebase`
  在第一次 push 之前都會失敗。skill 沒提「repo 還是空的」這個起點。
- 建置速度的標準(一分鐘算快)在 CI 上輕鬆達標(build 約 10 秒)。本機第一次要下載 Hugo,
  這次因為連線慢花了 6 到 9 分鐘;之後每次 `make check` 不到 1 秒。

### 三支一起用

- 三支各有一段「完成後的回報」格式,合起來的回報很長,而且內容互相重疊
  (切法、建置證據、commit 清單各被要求講一次)。這次合併成一份,同一件事只講一次。

## 功能 2:基本版面(2026-10-05)

### double-diamond-principle

**有幫助**

- 「Discover 縮成查核:規格有沒有和現況矛盾」這次查出三處。規格只寫「先看分享圖上有沒有舊字樣」,
  實際打開圖,舊網域與舊標語都印在上面;「選單先只放已經存在的頁面」照做的話選單是空的;
  原架構的標語只對得上六個分區裡的三個。三件都是打開實物才知道,讀規格讀不出來。
- 「先小規模試,驗最不確定的那一點」:驗收寫「360px 沒有橫向捲動」,拿首頁量一定會過。
  在暫存區搭了一個放長網址、長程式碼、寬表格、9 個選單項目的測試站,才量到原樣式的缺口。
  同一個測試站順便把還沒輪到的樣式(文章列表、搜尋、目錄)照原版型的結構擺出來看過一次。
- 「把選項攤開來,用使用者看得懂的方式呈現」:要站主決定的四件事(標語、分享圖、預覽標記、要不要上線)
  一次問完,分享圖與外觀都附了真的畫出來的圖。站主選了和建議不同的標語,問這一題是值得的。

**卡住或多餘**

- skill 的順序是「brief 先給使用者確認,再往下走」。這次反過來:先把不受答案影響的部分做完、
  把候選圖畫出來,再帶著實物去問。原因是這幾題用看的比用講的快。
  skill 提到「早期的製作可以是 Discover 的一部分」,但沒有說「帶著成品去確認」算不算合格的確認時機。
- Develop 這一步,真正有得選的是「`main.css` 整份先進來」還是「每項功能各帶各的樣式」。
  規格已經寫明前者。想過後者(每一筆都沒有用不到的樣式),最後照規格做,
  只把「之後哪一項要刪用不到的樣式」記下來。skill 沒有說「規格已經替你選好的事,還要不要攤開重選」。
- 紀錄和上一項一樣,寫回既有的 `features.md` 與 `requirements.md`,沒有另開一份。

### git-conventional-commit

**有幫助**

- 「拆完的每一筆都要能獨立通過建置」加上「不要動手寫出一個沒人跑過的中間版本」,
  兩條合起來決定了這次的拆法。三筆(版面、404 頁、分享圖)都動到 `hugo.toml`,
  做法是把後兩筆的檔案先移到暫存區、把 `hugo.toml` 改回那個階段的樣子,
  **真的跑一次 `make check`** 再提交,然後一筆一筆把東西放回來。每個中間狀態都實際建置過。
- `--range origin/main..HEAD` 在 push 前一次檢查三筆,很順。

**卡住或多餘**

- skill 給的拆法是「匯出 patch、刪減、`git apply --cached`」。那樣 stage 進去的內容和工作目錄不一樣,
  `make check` 跑的是工作目錄,等於提交了一個沒建置過的狀態 —— 正好是 skill 自己警告的事。
  建議補一句:用 patch 拆的時候,要怎麼驗那個只存在於 index 裡的版本。
- type 表對「一張圖加上產生它的腳本」沒有明確的位置。選了 `feat`(之後社群分享會用到),
  但這一筆當下沒有任何頁面引用那張圖。

### trunk-based-development

**有幫助**

- 「整合完成 = 落地後 trunk 的 CI 是綠的」之外,這次多做了一步:把線上的每個檔案抓回來和本機成品逐位元比對,
  六個檔案全部相同。404 的行為也只有在線上才驗得到(本機的靜態伺服器不會回自訂的 404 頁)。
- 「整合是會影響其他人的動作」那一段:push 到 `main` 就是公開部署,而這一項又需要站主看外觀,
  所以 push 之前先問了一次。

**卡住或多餘**

- 第 4 步的 `git pull --rebase` 在工作目錄有未提交的變更時直接失敗(「請提交或貯存修改」)。
  skill 的順序是「做一小步 → 帶入最新 trunk → 建置 → 整合」,沒說這時變更該是已提交還是未提交。
  這次改用 `git fetch` 後比對 `HEAD` 與 `origin/main` 的 SHA。
- 三筆 commit 一次 push,CI 只跑了最後一筆。中間兩筆只有本機驗過。
  skill 說整合要小而頻繁,但沒說「幾筆一起推」時中間那幾筆算不算整合過。
  這個 repo 每次 push 都是一次公開部署,所以選了一次推完。
- 建置速度:本機 `make check` 不到 1 秒;CI 的 build 7 秒、deploy 12 秒,整個 run 從開始到結束 28 秒。

### 三支一起用

- 三支 skill 都沒有提到「驗證用的背景行程要收掉」。這次為了截圖開了本機伺服器與無頭瀏覽器,
  做完自己記得關,並確認兩個埠都沒有人在聽。

## 功能 3:文章頁的閱讀體驗(2026-10-05)

### double-diamond-principle

**有幫助**

- 「Discover 縮成查核:規格有沒有和現況矛盾」這次查到一處真的矛盾:規格把「分區目錄」列在範圍內、
  「分區列表頁」列在範圍外,但有分區目錄 Hugo 就會產生分區頁,沒有列表版型建置會直接失敗。
  在暫存區的小站十分鐘內試出三條路(關掉 section 這一種頁面/先放一個精簡的列表版型/用 front matter 讓它不渲染),選了第一條。
- 「先小規模試」加上功能 2 留下的那句「用內容夠刁鑽的頁面量」,這次抓到三個原版型一直有的問題:
  深色模式的程式碼標點看不見、複製鈕多複製空行、中文閱讀時間恆為 1 分鐘。
  複製鈕那一個尤其說明問題 —— 驗收只寫「複製鈕可用」,按下去顯示「已複製」就會被當成通過;
  是把剪貼簿的內容讀回來和原始碼比對,才看到每行中間多了一個空行。
- 「把選項攤開來,用使用者看得懂的方式呈現」:發布前只問了一題(現在發布/先以草稿進 repo/先不進 repo),
  附上文章大綱。其餘的決定(分區、網址規則、連結寫法、表格)都有實測可以依據,沒有拿去問。

**卡住或多餘**

- 站主填的需求是「第一篇文章的題目與內容:claude mod簡易測試與說明」—— 只有一句,題目和內容是同一句。
  skill 說「能問使用者的事就直接問」,但這時候問等於把整件事卡在第一步。
  這次的做法是先用環境裡的證據判斷它指的是什麼(Claude Code 內建了寫 mod 的說明),實際做一次測試、把文章寫出來,
  到「要不要公開」那一刻才問。skill 沒有區分「一開始就該問」和「可以帶著成品再問」的問題;
  功能 2 的心得寫過同一件事,這次又遇到一次。
- Develop 與 Deliver 這次分不開。每個小決定(網址規則三種寫法、站內連結兩種寫法)都是「列出來 → 當場各建一次 → 看產出」,
  幾分鐘就有答案,沒有「先攤開選項、再另外找時間小規模測試」這兩步。skill 的四階段在這種規模的決定上是同一個動作。
- 「只用三支專案 skill」這條規則和這一項的內容有一處擦邊:文章的主題是 Claude Code 的 mod,
  要寫得正確只能去讀 Claude Code 內建的那份 mod 說明。這次把它當成文章的資料來源來讀,開發流程仍然只照三支 skill。

### git-conventional-commit

**有幫助**

- 「有幾種性質不同的事」這個判準把這次切成三筆:文章頁(版型、樣式、設定)/文章範本與發文說明/文章本身。
  前兩筆一起 push,第三筆單獨 push,所以「發一篇文要多久」量到的是只有一篇文章的那一次。
- 沿用功能 2 的做法:要提交哪一筆,就把不屬於它的檔案移到暫存區,對著那個狀態真的跑一次 `make check` 再提交。

**卡住或多餘**

- **type 表沒有「發一篇文章」的位置**。這個 repo 的產品就是文章,`docs` 已經用在開發文件上,`feat` 又不是。
  這次自訂了 `post:`,檢查腳本給 WARN。skill 對 scope 說「repo 沒在用就不要自己發明」,對 type 只說「規範允許自訂」,
  沒有說內容型的 repo(部落格、文件站)該怎麼分。建議補一段。
- 原版型的三個問題是和文章頁同一筆 `feat` 進來的,沒有另外切成 `fix`:
  那幾個檔案要嘛這一筆才第一次進 repo(複製腳本),要嘛在這一筆之前根本沒有生效(語法樣式)。
  「修的是還沒在這個 repo 上線過的東西」算 `fix` 還是算 `feat` 的一部分,skill 沒有寫;這次寫在 commit 的內文裡。

### trunk-based-development

**有幫助**

- 「整合完成 = 落地後 trunk 的 CI 是綠的」之外照舊多做一步:兩次 push 之後都把線上的每個檔案抓回來和本機成品逐位元比對(6 個、8 個,全部相同)。
- 切法帶來一個好處:版型先上線、確認綠燈之後,文章才單獨推。文章那一筆如果有問題,要還原的只有一個 Markdown 檔。
- 建置速度:本機 `make check` 不到 1 秒;CI 整個 run 約 20 到 30 秒;文章從 `git push` 到公開網址回 200 是 24 秒。

**卡住或多餘**

- 和功能 2 一樣:工作目錄有未提交的變更時 `git pull --rebase` 不能跑,改用 `git fetch` 比對 SHA;
  兩筆 commit 一起 push,CI 只跑了後面那一筆。
- 這個 repo 的 push 同時是整合也是發布。skill 把「發布」寫成 release branch 或打 tag 的事,
  對「每一次整合都直接公開」的專案,沒有說哪些整合需要先問人。這次的分法是:版型照既定流程直接推;
  以站主名義公開的文章內容先問。

### 三支一起用

- 背景行程的收尾這次出了一次錯:用 `pkill -f <特徵字串>` 關本機伺服器,特徵字串也出現在自己那一行指令裡,
  結果把執行指令的 shell 一起關掉,伺服器反而還活著。第二次改成從 `ss -ltnp` 找出佔用埠的 PID 再關,
  並確認兩個埠都沒有人在聽。三支 skill 都沒有提收尾,這件事功能 2 的心得已經寫過。
- 為了寫文章,實際跑了三次不互動的 Claude Code(小模型),會算在站主的用量上。
  skill 沒有涵蓋「驗證本身要花別人的額度」這種情況;這次是照最小的量做,並在回報裡說明。

## 功能 4:被找到與被訂閱(2026-10-05)

> 這一項用的是三支 skill 的**第三版**(依功能 1 到 3 的心得修訂過)。
> 另外要說明:這一項不是在新對話裡做的 —— 同一個對話稍早才讀過前三項的心得、檢視過舊版 skill,
> 所以 agent 開工前就知道哪幾段是新改的。下面的觀察沒有前三項那麼獨立。

### double-diamond-principle

**有幫助**

- 新的那一列「規格就是 brief,不要另寫一份;新學到的事寫回原文件」把前三項每次都要想一下的事變成不用想。
  這次直接從查核開始,紀錄寫回 `features.md` 與 `requirements.md`。
- 查核照舊最有價值,這次四件事都是規格讀不出來的:子路徑下的 `robots.txt` 爬蟲不會讀;
  規格要的檢查「不得含 `http://`」會被 sitemap 自己的命名空間擋下;原版型的 RSS 原樣搬是空的而且無效;
  之後打開分區頁會多出一堆重複的 feed。
- 「先小規模試」這次多做了一個對照組:把原版型的寫法原樣送 W3C 驗證器,先看到它回報 3 個錯誤,
  才相信候選版的「0 個錯誤」不是驗證器什麼都放行。驗證器還抓到一個自己沒想到的問題
  (RSS 的說明欄要多跳脫一層),修的過程又發現 `truncate` 會偷偷做一次跳脫。
- 新的「什麼時候問」那一段:照它分類之後,這一項沒有任何一題需要在動手前問。
  唯一和站主有關的事(要不要去站長工具提交 sitemap)不影響做法,放在回報的最前面。

**卡住或多餘**

- 「規格已經選好的不必重選,除非查核發現它行不通」—— `robots.txt` 正好落在中間:
  它不是行不通(建得出來、內容正確),是**做了也沒有作用**。skill 沒有說這種情況要照做、要拿掉、還是要先問。
  這次照規格做、把限制寫進檔案的註解與文件、在回報裡講明。
- Develop 仍然只有小決定(分享標題要不要帶站名、feed 的宣告放哪幾頁、說明文字誰負責跳脫),
  每一個都是當場建一次看產出。新的那句「只攤開規格還沒決定的事」和實際做的一致,這次沒有硬湊方案的感覺。
- 驗收要用外部服務(W3C 驗證器),等於把內容送到站外。這次送的都是本來就要公開的內容,而且文章已經在線上;
  skill 沒有提「小規模測試會把東西送出去」時要先想什麼。

### git-conventional-commit

**有幫助**

- 新加的 `git checkout-index -a --prefix=…` 那一段用在第三筆:全部 stage 之後匯出,在匯出的那一份上跑 `make check`。
  它還有一個沒寫到的用處 —— 那個目錄是丟棄用的,驗「草稿不會進 feed」時直接在裡面加假草稿,
  不必在 repo 裡建檔再刪。
- 「測試跟著它驗證的那筆變更走」:成品檢查每一片都要擴充,三次都跟著那一片的 `feat` 一起提交,
  沒有另外切一筆 `test`。
- 這次沒有用到拆 commit 的任何技巧。做法是「做一片 → 提交 → 做下一片」,每一筆提交時工作目錄裡沒有別的東西,
  所以不需要事後拆。前兩項是全部做完才回頭拆,這次順很多。

**卡住或多餘**

- **匯出的目錄裡沒有被 gitignore 的建置相依**。這個 repo 的 Hugo 下載在 `.hugo-bin/`,不在 index 裡;
  直接在匯出的目錄跑 `make check` 會重新下載一次(功能 1 量過,連線慢時要 6 到 9 分鐘)。
  這次是手動連一個 symlink 過去。`node_modules`、下載下來的工具鏈都會遇到同一件事,skill 的那一段沒提。
- skill 的範例路徑是 `/tmp/staged`。這個環境要求暫存檔放在對話專屬的目錄,所以改了路徑;小事。
- 收尾那一筆同時有開發紀錄、README 與文章範本裡的一行註解。範本不算文件,但改的只是寫給作者看的說明,
  歸在 `docs`。type 表對「程式檔裡只改了說明文字」沒有明講(`docs` 寫的是「只改文件」)。

### trunk-based-development

**有幫助**

- 循環的新寫法(第 3 步先在本機 commit,第 4 步才 `pull --rebase`)三次都一次過,
  前兩項每次都撞到的「請提交或貯存修改」這次沒有出現。
- 發布表新增的那一列(每次整合就是發布)直接回答了「這三次 push 要不要先問」:
  照規格做的版型與設定,建置為綠就推;沒有以站主名義對外的內容。前一項是自己想出這個分法的,這次有依據。
- 新的 `git ls-remote --symref origin HEAD` 一次就有答案。
- 這次三片分三次 push,每一筆都有自己的一次 CI(24 到 28 秒,全綠),不再有「中間幾筆只有本機驗過」。
  每一片也都是單獨有用的東西(分享預覽/可訂閱/sitemap),線上不會出現做到一半的狀態。

**卡住或多餘**

- skill 沒有說「上一次 push 的 CI 還在跑,能不能推下一筆」。這次每次都等前一筆變綠才推下一筆
  (中間剛好在做下一片,沒有空等),這樣哪一筆弄壞的一看就知道。
- 三次 push 等於兩分鐘內公開部署三次。skill 鼓勵小而頻繁,對「每次整合都是發布」的專案沒有說頻率有沒有上限
  (訂閱 feed 的人、快取分享預覽的平台會在中間的狀態進來)。這次的三片彼此獨立,所以沒有問題。

### 三支一起用

- 三支都加了「合成一份回報」那一句,這次的回報只有一份,切法、建置證據、commit 清單各講一次。
- 背景行程:這次只開過一次無頭瀏覽器截圖,用 `timeout` 包起來一次跑完,結束後確認沒有殘留的行程。
  三支 skill 仍然沒有提收尾;這次沒有出事,是因為沒有開常駐的伺服器。
- 三支 skill 都沒有處理「驗收條件裡有一項只有使用者能做」的情況(站長工具要用站主的帳號)。
  這次的做法是把其餘驗收做完、那一項明講沒做、寫清楚要做的話怎麼做。

## 功能 5:分區與首頁列表(2026-10-05)

> 這一項是在新對話裡做的,用的是三支 skill 的第三版。開工前讀過前四項的心得。

### double-diamond-principle

**有幫助**

- 「Discover 縮成查核」照舊是最值得的一步。逐檔讀來源版型時看到首頁的分區卡片是從選單網址切字串,
  對照功能 1 的實測表就知道它在子路徑下會對不上;這個問題不會讓建置失敗、連結檢查也看不出來,卡片只是安靜地不見。
  另一件是規格的目標寫「可以分頁與排序」,而原版型的設計是兩者不會同時出現 —— 讀規格會以為是兩個疊在一起的功能。
- 「只攤開規格還沒決定的事」:這一項規格明寫留下一個決定(空的分區要不要掛選單)。攤開三個做法
  (全部掛/照原架構手動註解/寫在設定裡但自動隱藏),選第三個的理由直接來自需求文件排第一的那件事 —— 發文不要有手動步驟。
- 「先小規模試」加上前幾項留下的「檢查器要先確認量得出問題」:這次做了兩個對照組。
  拿修之前的成品餵新的檢查器(4 個問題),再確認修完會過;拿原版的排序腳本在瀏覽器裡按一次,
  看到同一天的兩篇在「最舊在前」時順序是錯的,才動手改。
- **第一次跑對照組是無效的**,而且差點沒發現:原版的測試站掛在另一個路徑底下,排序腳本的網址帶著子路徑,根本沒載到,
  所以「按了沒有任何變化」。是因為輸出裡順手印了 `localStorage`(是空的)才看出腳本沒有執行。
  skill 講了「小範圍測試」,沒有講「對照組自己也要先確認有跑到」。

**卡住或多餘**

- **「這一項決定」是誰決定?** 規格這一項沒有「需要站主」那一行,所以把選單的決定當成留給實作的人,
  照原架構的方向做完、放在回報的最前面。但選單是讀者第一眼看到的東西,照 skill 的分類它屬於「用看的比用講的快」,
  期限是公開之前 —— 照字面應該帶著截圖先問再 push。這次沒有問,理由是規格沒要求、方向和原架構一致、改回去是一行設定。
  skill 沒有區分「規格留給實作者的決定」和「要使用者確認的決定」。
- **版型需要文案,但沒有人給**。分區卡片上的一句話與列表頁開頭的介紹,原架構有、站主說舊內容不帶。
  自己寫等於替站主說話,問又會把整項卡住。這次是版型支援、內容留空、回報裡附上建議的寫法。
  skill 對「做法定了、但缺一塊只有使用者能給的內容」沒有說法(功能 4 的 sitemap 提交是同一類)。
- Develop 與 Deliver 仍然分不開,和功能 3、4 的觀察一樣。

### git-conventional-commit

**有幫助**

- `git checkout-index -a --prefix=…` 三筆都用了:這次是三片都做完、實測完才回頭切,工作目錄一直比 index 多東西,
  沒有這一步就是在提交沒建置過的狀態。
- 檢查腳本四筆都一次過,沒有 WARN。

**卡住或多餘**

- **兩條規則這次互相拉扯**。第一、二筆需要一份「還沒有『最新』選單項目」的 `hugo.toml`(少四行),那是動手改出來的中間版本;
  skill 一邊說「得由你動手寫出中間版本就不要拆」,一邊給了能驗證中間版本的匯出技巧。
  這次照前幾項的做法:改出來、在匯出的目錄跑過 `make check` 才提交。skill 沒有說「驗證過的中間版本」算不算可以拆。
  功能 4 的心得寫過更好的解法(做一片就提交一片),這次沒有照做,是因為三片共用同一個測試站、想一次驗完。
- 匯出的目錄沒有被 gitignore 的建置相依(`.hugo-bin/`),仍然要自己連 symlink。功能 4 提過,skill 還沒有補。
- 原版型的問題(卡片對不上、canonical、同一天的排序)都跟著它所在的那一筆 `feat` 進來,沒有切成 `fix`,
  理由和功能 3 相同:那些檔案是這一筆才第一次進 repo。唯一的例外是 `head.html` 的 canonical ——
  那個檔案功能 4 就在了,但在這一筆之前沒有任何會分頁的頁面,所以也不算修一個已經上線的 bug。

### trunk-based-development

**有幫助**

- 第 4 步的 `--autostash` 這次正好用上:提交第一、二筆時工作目錄裡還有後面幾片沒提交的檔案,
  `git pull --rebase --autostash` 一次過。
- 三片分三次 push,每次等上一筆的 CI 變綠才推下一筆(整個 run 27 到 48 秒)。每一片推上去之後站都是完整的:
  第一片之後有分區頁而首頁還是暫時的清單,第二片之後首頁換新,第三片多出「最新」。
- 「整合完成 = trunk 的 CI 是綠的」之外照舊把線上 25 個檔案抓回來和本機成品逐位元比對,再用瀏覽器量一次線上的頁面。

**卡住或多餘**

- **第一片偏大**(18 個檔案):列表、摘要卡、分頁、排序、選單過濾、canonical 的修正與檢查器。
  其中 canonical 那一塊可以先單獨送一筆(它不依賴列表頁),這次沒有拆。skill 的「夠不夠小」是以時間計的,
  對「檔案多但彼此少了誰都不成立」的一片沒有別的判準。
- **驗收要用假資料,而假資料絕對不能進 trunk**。規格寫「用假文章驗,驗完移除」;這次根本沒有把假文章放進 repo,
  而是把工作目錄複製到暫存區、在那裡加 25 篇假文章建置。這樣不會有「忘了移除就推上去」的機會。skill 沒有提這種情況。
- 這個 repo 的 push 就是公開部署。照 skill 的分法(照規格做的版面變更直接推、以站主名義對外的內容先問),
  這次三筆都直接推了;分區的標題與「最新文章」這幾個字算版面還是算文案,是自己判斷的。

### 三支一起用

- **本機的測試打到了線上的站一次**。Hugo 替分頁產生的轉址頁用的是寫死的完整網址,本機瀏覽器打開它就被帶到
  `yongrui0402.github.io`(當時那一頁還沒部署,回 404)。只是一次讀取,沒有副作用;
  但三支 skill 都沒有提「本機驗證可能碰到正式環境」。
- 背景行程:開了兩個本機靜態伺服器與一個無頭瀏覽器,做完用 `ss -ltnp` 找出佔用埠的 PID 逐一關掉,並確認三個埠都沒有人在聽。
  沿用功能 3 記下的做法,這次沒有出錯。三支 skill 仍然沒有提收尾。
- **做的過程中沒有主動回報進度**,被提醒了好幾次。三支 skill 都只規定「完成後的回報」,
  對一段要連續實測幾十分鐘的工作,中途該講什麼、多久講一次,沒有任何指引。

## 功能 6:標籤(2026-10-05)

這一項不大:兩筆 `feat`、一筆 `docs`,動到 10 個檔案。

### double-diamond-principle

**有幫助**

- 「Discover 縮成查核」這次是先在暫存區造一批刁鑽的假標籤(大小寫衝突、中文、`C#`、`CI/CD`、含空白、數字),
  在寫任何版型之前先看 Hugo 實際怎麼處理。三件事都是這一步看到的,讀版型讀不出來:
  原版型的連結寫法對 `C#` 是壞的、Hugo 有現成的設定可以取代 `term-name`、寫法衝突時名稱每次建置不一樣。
- 「Develop 只攤開規格還沒決定的事」讓這一步很短:真正要選的只有連結怎麼組、名稱怎麼還原、衝突怎麼辦三件,
  每一件都是拿實測結果選的,沒有硬湊方案。
- 功能 5 留下一個標成「推測,沒有實測」的句子;這次順手驗掉了(成立)。「把假設列出來、標明哪些是猜的」
  的好處是下一個人知道該驗什麼。

**卡住或多餘**

- **規格選好的做法可行,但查核發現有更簡單的** —— skill 只說「規格已經選好的不必重選,除非查核發現它行不通」。
  `term-name` 不是行不通,是不需要。這次自己決定不搬、寫在回報最前面;skill 沒有這一格。
- **「寫法衝突時讓建置失敗」是誰的決定?** 它會讓站主的 push 多一種失敗的原因,照 skill 的分類比較接近
  「答案會改變方向的」,應該先問。沒有問的理由:不擋的話成品不固定,那是已經講好的驗收條件;改回去是刪一行。
  和功能 5 記下的是同一個問題 —— skill 沒有區分「規格沒料到、實作時冒出來的決定」該不該停下來問。
- Develop 與 Deliver 仍然分不開:三個選擇都是「試了才知道」,試完也就選完了。

### git-conventional-commit

**有幫助**

- 兩筆 `feat` 動到的檔案完全不重疊,以檔案為單位 stage 就是正確的中間狀態,不必動手寫中間版本
  (功能 5 卡過的那個問題這次沒有出現 —— 是切法剛好避開,不是 skill 解決了它)。
- 第一筆照舊用 `git checkout-index` 匯出來單獨跑 `make check`;第二筆 stage 之後工作目錄已經等於 index,直接在原地跑。

**卡住或多餘**

- 匯出的目錄仍然要自己把 `.hugo-bin/` 連過去(功能 4、5 都提過)。
- 第一筆裡有兩處其實是「修問題」(分頁的 canonical、總覽的橫向捲動),都跟著 `feat` 進來:
  標籤頁在這一筆之前不存在,沒有「已經上線的壞行為」可以修。和功能 3、5 的判斷相同;skill 的 type 表沒有講這種情況。

### trunk-based-development

**有幫助**

- 兩筆分兩次 push(第一次用 `git push origin <sha>:main` 只推前一筆),各等 CI 變綠(27、28 秒)。
  順序是「頁面先上、連結後上」:第一筆之後標籤頁從頁尾進得去,第二筆才讓文章上的標籤指過去,中間沒有任何時刻有壞連結。
- 假文章從頭到尾沒有進 repo:寫了一支小腳本把工作目錄複製到暫存區、再疊上假文章,改一次版型就重建一次。
- 本機的瀏覽器測試這次沒有打到線上:靜態伺服器掛在和線上相同的子路徑底下,也沒有去開 Hugo 產生的轉址頁(功能 5 踩過)。

**卡住或多餘**

- skill 沒有提「本機有好幾筆 commit 時只推前面幾筆」的寫法,是自己想到的。
- **線上的內容不足以驗收**:驗收有一條「中文標籤的網址打得開」,線上沒有中文標籤的文章,而假文章不能推上去。
  這次如實回報「只在本機驗過」。skill 的「整合完成 = trunk 的 CI 是綠的」沒有涵蓋「綠了,但驗收條件在線上看不到」。
